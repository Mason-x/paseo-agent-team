# 发布流程

编写：2026-11-09。依据：`docs/run-engine-todo-plan.md` 4.3、4.4、4.9。适用于 `paseo-agent-team` 插件的所有代码 PR 与发布。

## 1. 分支与提交

- 每个任务一个分支，从当时最新的 `origin/main` 切出，命名为 `todo/t<n>-<slug>`；同一个 worktree 同一时刻只有一个写者。
- 提交信息用英文，类型遵循约定式提交（`feat`、`fix`、`test`、`docs`、`chore`，可以带作用域）。
- **禁止破坏性标记**（`!:` 或正文里的 `BREAKING CHANGE`）：在 0.x 阶段它会让 release-please 把版本直接升到 1.0.0。
- 用 `git commit -F <消息文件>` 提交，末尾写该会话被要求的署名行；改过的文件保持 LF 换行。
- 实施会话只在本地提交：不 push、不开 PR、不合并、不打标签、不改版本文件和 `CHANGELOG.md`。

## 2. PR 与合并前置条件

协调者负责 push 并开 PR：

```text
git push -u origin <分支>
gh pr create --base main --title "<约定式标题>" --body-file <文件>
```

PR 正文写清做了什么、没做什么、合同变化、测试数、变异与评审记录的路径、回滚办法。

合并前必须全部满足：

- PR 上 `CI sentinel` 成功；
- 另一个模型的新会话独立重跑门禁 G 通过；
- 任务要求的评审已通过，确认的问题要么已修复，要么已登记为已知限制；
- 分支跟上了 `main`。没跟上就 `gh pr update-branch <n>` 更新，**用合并方式更新，不要 rebase**（文档里引用了分支提交的 SHA），然后等 CI 重新变绿。

## 3. 合并命令

统一用 merge commit，并把正文改写成非约定式文字，避免变更日志出现重复条目：

```text
gh pr merge <n> --merge --subject "Merge pull request #<n> from Mason-x/<branch>" --body "Changelog entries come from the branch commits."
```

不用 squash，不用 rebase，不 cherry-pick。合并后用 `gh run list --branch main --limit 2` 确认 `main` 的 CI 是绿的；分支保留，不手动删除。

**直推 `main` 禁止。** T2 的 ruleset 修改（由协调者在 PR 合并后执行）会把 `bypass_actors[0].bypass_mode` 从 `always` 收紧为 `pull_request`，只有经由 PR 才可能使用绕过。

## 4. 发版（Release Please）

1. 用 `gh pr list --label "autorelease: pending"` 找到 Release Please 的发布 PR。
2. 用 `gh pr diff <n> --name-only` 核对：diff 只应包含 4 个发布文件（`.release-please-manifest.json`、`paseo-agent-team/CHANGELOG.md`、`paseo-agent-team/package-lock.json`、`paseo-agent-team/package.json`）。读 `CHANGELOG.md` 片段，确认版本符合预期、条目与已合并的 PR 一一对应、没有重复。有重复说明当初合并时没有按第 3 节改写正文：记下来，但不手改。
3. **触发发布 PR 的 CI**：这类 PR 由 `GITHUB_TOKEN` 创建，检查不会自动出现。以 `Mason-x` 身份关闭再打开：

   ```text
   gh pr close <n>
   gh pr reopen <n>
   gh pr checks <n> --watch
   ```

   等 `CI sentinel` 成功（插件作业会在 Linux 上跑全量 coverage）。10 分钟内检查没有出现，就再关闭、打开一次；仍然没有，才按第 6 节判断能否绕过。
4. 合并发布 PR：

   ```text
   gh pr merge <n> --merge --subject "Merge pull request #<n> from Mason-x/release-please--branches--main--components--paseo-agent-team" --body "Release PR; changelog generated by Release Please."
   ```

5. 等 `main` 上的 Release Please 工作流完成，确认 `gh release view paseo-agent-team-v<版本>` 与标签都存在、`main` 的 CI 是绿的。
6. 可选：在 GitHub release 正文末尾追加回滚注意。先 `gh release view --json body` 取原文，追加后用 `gh release edit --notes-file` 写回；不改 `CHANGELOG.md`。
7. 在实施 worktree 里 `git fetch --tags`。**不动主工作区，不对真实实例做 reload 或 update**；用户用插件自带的版本流程更新。

## 5. 版本规则

- 版本由 release-please 按约定式提交计算：`feat` 升次版本，`fix` 升修订版，文档和测试不单独立版。0.x 阶段禁止破坏性标记。
- 发版节奏：
  - 每批任务合并后发一次；
  - DEV 发现的问题修好后发修订版；
  - 一天之内最多发一次；
  - 每次发版前，自上次发布以来必须有 `feat` 或 `fix` 提交；
  - **不再手工发版**。

## 6. 绕过（管理员合并）

只限**发布 PR**，并且以下条件同时成立：

- 已经关闭再打开了两次，每次等 10 分钟都没出现检查（或者 GitHub Actions 本身故障）；
- diff 只含那 4 个发布文件；
- `main` 最新提交的 CI 是绿的；
- 版本号符合预期。

合并后 `main` 的 CI 必须是绿的；不绿就立刻开 revert PR。并在协调者状态文件和本文的“绕过记录”里各记一条。**代码 PR 绝不绕过**：CI 不绿就修复，或者撤回。

## 7. 回滚

- **还没合并**：逐个文件 `git restore --source=HEAD`，删除新增的文件；不用 `git stash`。也可以直接放弃这个分支，切回 base 分支，分支本身保留不删。
- **合并之后才发现问题**：开 revert PR（`git revert -m 1 <合并提交>`），走同样的 CI 和合并规则。发布本身不撤：严重缺陷就 revert 后再发下一个修订版，README 和发布说明写明怎么回到上一个版本（在插件的版本流程里选旧版本）。
- ruleset 改错时，用修改前保存的 JSON 内容 PUT 回去。

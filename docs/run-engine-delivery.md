## 1 怎么打开

1. 在**启动真实 daemon 的那个环境**里设 `PASEO_AGENT_TEAM_RUN_ENGINE=1`，重启 daemon。不设这个变量时，开了 Run 引擎的 Team 会被拒绝启动，不会静默退回协调者链路。
2. 再在 Team 里单独启用 Engine（Team 编辑器的 Run 引擎一节）。
3. 真实实例的启用和重启由用户安排，挑没有在途 Agent 的时候做：重启会打断在途回合，插件冷编译约 2 分钟。
4. 同一件事的英文说明在 `paseo-agent-team/README.md` 的 Run Engine 一节；两处冲突时以发布版本的代码为准，并回报。

## 2 重启之后怎么办

- **先打开 Runs 页。** 插件加载时拿不到 Paseo 句柄，恢复是惰性的：没人调用插件，活着的 Run 就不动。
- Engine 会按台账重开已关闭的席位；打不开的成员按启动时冻结的规格重建。重开只读历史，不发消息、不调用模型。
- **回复丢了**：先等至少 30 秒，再点“立即检查并推进”。
  - 先看这个任务的分支：上一次尝试可能已经提交了改动，重试会在现有分支上接着做。
  - 确认成员进程已经停了，再决定重试或取消。
- 协调者没加载时重建会失败（见 3.1），只能取消这个 Run 后重新启动。
- 派发结果不明而冻结的 Run，出路见 3.3；不要反复点按钮等它自己好。

## 3 冻结与已接受的残余（0.8.0）

**3.1 协调者未加载时，重建记为 `create-failed`。** 宿主报 `Caller agent … not found`，`errorCode` 只把消息里含 `parent` 的错误归入 `parent-unavailable`，所以不会先重开协调者。Run 停在告警处，只能取消后重开；取消可以完成（B′，N=1）。T11b 的优雅重启路径同样可能受影响（推断，未验证）。这个分类缺陷自 T11b 起就在 main 上，撤回 E2b 也去不掉；0.8.1 的窄修复（只改这一处分类，合同零变化，带 1 个 DEV Run）尚未开始，排在 M1 之后、M2 之前。

**3.2 E2b 是部分通过，不是通过。** 已观察到：读历史失败一次；对旧 Agent 零派发（台账没有它的 outbox 或 assignment，宿主 `lastUserMessageAt=null`；它的时间线读不出来，只算部分佐证）；失败后有告警；取消走到 `cancelled`（rev 38）并释放占用（N=1）。未达到：新评审完成、Run finished。第一轮 Run B 没有 E2b：取消停在 paused，`repo-exclusive` 占用保留。两者必须区分。

**3.3 派发结果不明（`outcome-unknown`）与最后出路。** 冻结残余的写法：只有崩溃那一刻正在发出的派发会这样（B′，N=1；窗口大小未测）。另一处同类观察：T11e Run B 强杀后给一个从没跑过回合、宿主列为 idle 的 Codex 评审派发，宿主报 `no rollout found`，派发停在 `outcome-unknown`，取消停在 paused、占用保留（N=1）。
最后出路：停 daemon，确认所有旧写者（含成员子进程）已停止，把台账文件移出 `agent-team-runs` 另存，再启动。**这一步只用真实 store 代码做过离线验证**（夹具含 `outcome-unknown` 的派发意图、paused 的 Run 和 `repo-exclusive` 占用），没有在活 daemon 上试过。停 daemon 和移出台账不能证明旧成员或子进程已停；确认旧写者停止前，不要让另一个 Run 写同一仓库。若新 Run 已取得相同占用，不要再把旧台账放回去。

**3.4 其余已接受的残余**（完整边界见验收表）：协调者的重建（第一个规划回合几秒内被打断时只能取消重开）；假空闲（读到 idle 不能证明成员能用）；冒烟、补证丢失的回合仍只能取消；惰性恢复；`SeatRead` 没有 archived 标志；优雅停机有时不写 `closed` 回执，停机后成员子进程可能还在跑；T5 原因草稿不跨 daemon 重启；浏览器检查用的是 Playwright Chromium，不是真实 Chrome；B13 完整续办、B7、B8、`run.export`、`assign-seat`、策略字段编辑入口、AC20 按原裁决推迟。E2a 另有两条：同一回合 id 在同一进程出现第 3 次时，重试回合的结束仍可能被丢掉（点一次“立即检查并推进”入账，期间没有告警）；被 Engine 结算过的回合，迟到的真实结束会归给已开始的重试回合。

**3.5 Runs 页的旧式成员卡会读时间线。** 展开它会重新打开已关闭的 Claude 成员（T11d 的 V1-3 就是这样被浏览器先打开的），所以观察期间不要靠展开旧卡来查状态；用只读的 `run.get` / `run.list`。

**3.6 CHANGELOG 的重复条目。** 0.8.0 有一条标题重复（`37b41bd` 与 `fad391c`），来由是 PR 用默认合并正文合并，Release Please 同时收下了分支提交与合并提交。按裁决不手改，以免和 Release Please 打架。

**3.7 omp 渠道没有 DEV 样本。** T8 起的 DEV Run 只用过 `claude-haiku-5-5` 与 `gpt-6-luna`；omp 的 token 与回合数据在对照里按 N/A 处理，先做探针。

## 4 回滚

- 在**没有在途 Engine Run、也没有未答复的恢复决策**时回退。
- 回到 0.7.x：冻结规格和重建记录被忽略，已换绑的席位照常用新 Agent；还在 `creating` 的重建会被丢下，可能留下一个没登记的 Agent；重试回合的结束要点“立即检查并推进”才入账；成员只是被关闭时开出的 `host-lost` 决策，答“重试”会停在已关闭的席位上（0.7.x 不会重开），应改答取消；崩溃之后从没开过回合的 Codex 成员仍会被派发并把 Run 冻结（有还没做过评审的 Codex 评审席时，在派发前先取消，取消完成后再重开；若已出现未知派发，取消可能停在 paused，占用仍保留）。
- 回到 0.7.1 的实测：评审的 `host-lost` 决策显示“重试”，但答复被拒（`decision-stale`）。回滚前先答复这类决策。
- 回到 0.6.x：`member-lost` 决策会显示“重试”，属于误导。

## 5 观察期里用户要做的事

**2026-11-12：本节不执行。** M1 判「Engine 不如」，Engine 冻结，观察期没有起算；以下为历史内容。

1. 在真实实例上开 Engine，自己启动 Run 做真实开发：至少 3 个由你亲自启动的真实 Run 跑到 finished 或取消完成，期间没有 `ledger-refused`，也没有不变式失败。
2. 计满 7 天：从你在真实实例上、于符合条件的版本启动的第一个 Engine Run 起算（D10-A）。0.8.0 及以后符合，因为现有残余都不属于“Run 卡死”类；观察期内出现这类缺陷，就从修复它的版本上第一个真实 Run 重新起算。
3. “Run 卡死”类指满足任一条：Run 无法经由文档写明的出路走到 finished 或 cancelled；Run 静默等待，既没有告警也没有决策；人没有选择取消，已交付的任务却丢了。
4. 准入表全部满足后合并草稿 PR 并发布 0.9.0，这是预先批准，不必再问架构师。但第 7 行目前是“拿不准”：需要 0.8.1 之后的一个 DEV 样本，没有就回问架构师；任何一行拿不准，都回问架构师，不得自行合并。
5. 团队没有碰过真实实例，也不代用户启动 Run；观察只用只读 RPC。

# 多 agent 协作最佳实践调研记录

- 调研日期：2026-11-12。配套文档：[PRD](prd.md)、[技术规格](spec.md)。
- 方法：外部资料由一个只读子 agent 通过网络检索收集；Paseo 的能力由主 agent 读官方文档和本机安装包核对。
- 要检验的假设：**每个任务一个写手、一个 worktree 和分支；其他 agent 只读（干净上下文、不同模型家族的审查者，侦察兵，调研员）；验收由程序执行；状态写文件；人决定合并；不做通用 DAG 调度；最多 3 到 5 个 agent。**

## 1 结论

1. **假设的主干成立。** "写入单线程、其他 agent 贡献判断而不是动作"是 Cognition 2026 年的原话级结论，Anthropic 的文档和研究文章给出了同方向的证据。
2. **有三处需要修正**，已写进 PRD 和 Spec：
   - "不同模型家族"的作用比预想的弱。稳定有效的是**干净的上下文**；跨家族带来的是互补覆盖，而且要求审查者本身是强模型。
   - 审查者会过度报告。审查意见要按任务说明筛选，循环要有轮次上限。
   - 测试通过不等于完成。门禁是必要条件，还要防止测试被删改，并且在合并后的结果上重新验证。
3. **用户原始笔记里的"约 43% 文本冲突"没有找到出处。** 最接近的已核实数字是 41.7%（不同 agent 的 PR 两两之间）和 27.67%（全部 agent PR）。

## 6 与假设不一致或需要补充的地方

| 发现 | 设计上的处理 |
| --- | --- |
| 跨家族本身的增益不显著，稳定的是干净上下文；轻量的跨模型审查者没有增益 | 干净上下文是硬要求。跨家族是默认偏好，同家族时只警告。审查者必须用强模型 |
| 一个同模型新会话加一个跨模型审查者，抓到的问题明显多于两个同模型审查者 | P1 的"第二审查者"按这个组合设计 |
| 审查者被要求找问题就总能找到；写手不筛选会打转 | 只有"阻断"级别的意见触发返工；写手可以对照任务说明逐条回应；轮次上限 3 |
| 测试通过不等于做完；agent 会削弱测试 | 受保护路径检查；任务说明模板强调验收命令要硬；这一条产品不能完全解决 |
| worktree 不是完整隔离，shell 写入可以越界，目标冲突的 agent 在共享设施上会互相破坏 | 一个 Run 内只有一个有写入目标的 agent；每个审查者一个独立的一次性 worktree，结论提交时再检查写手的 worktree 有没有被动过；文档写明端口、数据库、凭证的共享情况 |
| 两条各自通过的分支合起来可能失败 | 合并一个后，其他待合并的 Run 要 rebase 并重新走门禁和审查 |
| 同模型的 agent 会趋同（分支名、思路） | 分支名和 Run 编号由程序生成；多个同模型的"独立意见"相关性高，不当作独立证据 |
| 大规模并行写入有成功案例，但都依赖机器可判定的参照和大量开销 | 不在本产品范围内。日常预期不以这类演示为准 |
| Agent Teams 的任务状态滞后会卡住依赖它的任务 | 状态从程序观察到的事实（git、进程、文件）推导，不靠 agent 更新 |

## 7 值得固化的设计规则

1. 每个任务只有一个能写的 agent。
2. worktree、分支名、端口、数据库名由程序分配，名称唯一。
3. "完成"只由程序设置：程序执行声明的检查命令，记录退出码、输出和提交。agent 的声明只作参考。
4. 保护门禁：标记删除或跳过测试、修改检查命令的改动；在合并后的结果上重新跑门禁。
5. 审查者用新会话，只看改动和任务说明。优先用另一个家族的强模型，不用轻量模型做唯一审查者。
6. 审查说明：对照任务说明查正确性，不管风格，按严重程度分级。写手按任务说明筛选。轮次上限 2 到 3。
7. 每份任务说明包含目标、输出格式、边界、文件归属。
8. 任务说明、计划、进度、交接都写文件。测试输出在消息里只给几行，完整日志放磁盘。
9. 默认 1 个写手加 1 到 2 个协作者，硬上限 5 个。空闲的 agent 立即关掉。
10. 两个写手做不同任务时，要声明互不重叠的文件范围，否则串行。
11. 每次合并由人批准。agent 之间的消息不算批准。
12. 每个循环都有时间、次数或 token 预算。从进程和文件状态判断任务是否停滞。

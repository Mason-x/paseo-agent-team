# Agent Team v2 产品需求（PRD）

- 状态：方向已由用户确认（2026-11-12，见第 10 节）。编写：2026-11-12。
- 配套文档：[技术规格](spec.md)、[调研记录](research.md)。
- 本文回答"为什么做、给谁用、做到什么算成"。实现细节在 Spec 里。

## 1 背景

### 1.1 v1 做了什么，结果如何

paseo-agent-team v1 用两个月做了一套通用的多 agent 编排：Role 与 Team 目录、Team 设计师、四档模式与模型分层、协调者链路，以及一个带台账和恢复机制的 Run Engine。

| 事实 | 数字 | 出处 |
| --- | --- | --- |
| 源码规模 | 约 7.2 万行，其中 Run Engine 约 2.7 万行 | 仓库统计，2026-11-12 |
| 测试规模 | 约 11.6 万行 | 同上 |
| 提交数 | 716（2026-09-10 起） | `git log` |
| 同任务对照结论 | "Engine 不如" | [M1 结果](../m1-results.md) |
| K1、K2 两臂质量 | 隐藏测试全过，盲审零阻断，两臂持平 | 同上 |
| K3 | Engine 卡死未交付，链路交付 | 同上 |
| 已接受的残余缺陷 | 十余条，多数出路是"取消后重开" | [交付说明](../run-engine-delivery.md) 第 3 节 |

### 1.2 问题出在哪

1. **方向与最佳实践相反。** v1 的目标形态是 15 个席位、5 个实现席位、一个协调者。调研里证据最充分的做法是单写手加只读协作者（见[调研记录](research.md)）。
2. **复杂度花在恢复上。** 在一个不提供"恰好一次"语义的宿主上维护持久状态机，每个崩溃时刻都要一条恢复路径。最后 40 个提交几乎全在补这类路径。
3. **门禁靠 agent 自述。** v1 解析回合末尾的结构化块来判断证据是否齐全。M1 里链路臂的三个最终候选都没有经过完整复审，系统没有拦住。
4. **从未和最简单的做法比过。** M1 比的是 Engine 和协调者链路。"一个 agent 加一次独立审查"这个基线没有数据，所以两臂是否值得那些 token 都无法回答。
5. **设计前提已经变了。** v1 立项时插件不能给 agent 提供工具，只能解析文本。Paseo 0.14 起插件可以直接给指定 agent 挂工具，宿主自己也带了 worktree、端口隔离、Agent Profile 和编排技能。

### 1.3 决定

重新实现编排内核，体量控制在 v1 的二十分之一以内。v1 冻结在 0.8.x。

## 2 目标与非目标

### 2.1 目标

- **G1** 让一个开发者能把一个边界清楚的任务交出去，拿回一条通过了验收命令、经过独立审查的分支，自己只需要做合并决定。
- **G2** "完成"由程序判定：验收命令由插件执行，审查结论绑定到具体提交。agent 说"做完了"不算数。
- **G3** 任何时候打开界面，都能看到现在在等谁、为什么、自己能做什么。不出现静默等待。
- **G4** 在真实任务上记录每个任务的轮次、人工介入次数和结果，供用户自己判断值不值。不做前置的对照实验。
- **G5** 代码小到一个人一天能读完：源码不超过 3500 行（原定 3000，2026-11-12 修订一次，原因见 Spec 第 4 节）。

### 2.2 非目标

- 不做通用的任务 DAG 调度。
- 不让多个 agent 同时写同一条分支。
- 不追求无人值守的自动恢复。卡住就停下来交给人。
- 不做 lead 或协调者 agent。
- 不做 Role 与 Team 目录、Team 设计师、模式与模型分层。
- 不自动合并、不自动推送。
- 不追求比宿主自带的 `/paseo-advisor`、`/paseo-committee` 更会"调研"。只读调研用宿主技能即可，v2 只在需要强制门禁的地方加东西。

## 3 用户与场景

**用户**：独立开发者，本机运行 Paseo，手里有多个模型订阅（Claude、Codex、DeepSeek、Grok 等），同时推进一到三件事。瓶颈是自己的审查时间，不是生成代码的速度。

| 场景 | 描述 | 优先级 |
| --- | --- | --- |
| S1 写加审 | 写好任务说明和验收命令，交给一个写手。写手做完，插件跑验收，换一个模型家族的审查者看改动。通过后通知我来合并 | P0 |
| S2 并行几件互不相关的事 | 同时开两三个 S1，各自一个 worktree 和分支。合并一个之后，其余的要在新基线上重新验证 | P0 |
| S3 卡住时接手 | 写手反复过不了测试，或审查来回三轮没结论。系统停下来，告诉我卡在哪，给我几个明确的选项 | P0 |
| S4 先派侦察兵 | 任务难、我自己也不确定从哪下手。先让一个 agent 试做一遍，代码扔掉，只留一份"动了哪些文件、坑在哪"的报告，再据此写任务说明 | P1 |
| S5 开工前并行调研 | 有两三个互相独立的问题要先搞清楚，各派一个只读 agent，报告写进文件，写手开工时读 | P1 |
| S6 排查 bug 时多假设对抗 | 几个只读 agent 各持一种假设，互相反驳，产出一份结论 | P2，优先用宿主的 `/paseo-committee` |

## 4 产品原则

1. **能用简单方案就不用复杂的。** 每加一个状态、一个角色、一个配置项，都要说明没有它会出什么具体问题。
2. **写手唯一。** 一个任务只有一个 agent 改代码，一个 worktree、一条分支、一个 PR。
3. **其他 agent 的改动不进入分支。** 审查、侦察、调研的产出都是文件。每个审查者在自己的一次性 worktree 里工作，可以跑测试、写探针，用完整个删除。
4. **验收由程序执行。** 插件跑命令、存输出、判结果。
5. **审查用干净的上下文，优先用不同家族的强模型。** 审查者看不到写手的对话。干净上下文是硬要求，跨家族是默认偏好。
6. **状态和交接写进文件。** 任务说明、进度、失败过的路、审查报告、门禁日志都有固定路径。提示里给路径，不转述内容。
7. **卡住就停，交给人。** 有上限（门禁次数、审查轮次、无进展时间），到了就停。
8. **合并由人决定。**
9. **并行数量按人审得过来多少来定。** 默认最多 3 个同时活跃的任务。
10. **用宿主已有的能力。** worktree、端口、Profile、子 agent 轨道、通知都用 Paseo 的，不重做。

## 5 功能需求

### 5.1 P0（第一个可用版本）

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR1 | 新建任务：选仓库和基线分支，填写任务说明（六节模板：要什么结果、相关代码在哪、约束、不做什么、不能碰的文件、怎么验证） | 缺"怎么验证"时不能启动 |
| FR2 | 启动前确认验收命令和受保护路径，确认后冻结 | 启动后改任务文件不影响门禁执行的命令 |
| FR3 | 启动时自动创建 worktree 工作区和分支，创建写手并下发任务 | 分支名由程序生成，不重名 |
| FR4 | 写手通过工具"提交送审"。有未提交改动时被拒并告知是哪些文件 | Spec AC1 |
| FR5 | 插件执行验收命令，保存完整输出。失败时把真实输出发回写手 | Spec AC2 |
| FR6 | 门禁同时检查：是否改了受保护路径（默认含测试目录和 CI 配置） | Spec AC3 |
| FR7 | 门禁通过后自动创建审查者：新会话，每个审查者一个独立的 worktree（检出候选提交），优先与写手不同家族。默认 1 个，启动时可以添加到最多 3 个，全部批准才算通过 | 同家族时启动对话框给出警告 |
| FR8 | 审查者通过工具给出结论（通过或打回）和报告文件。意见分"阻断"和"建议"，只有阻断项触发返工。打回时报告路径发给写手，写手可以逐条回应 | — |
| FR9 | 审查结论绑定提交。批准之后写手再提交，批准失效 | Spec AC5 |
| FR10 | 审查者的 worktree 在结论提交后删除，里面的改动全部丢弃，只保留报告。审查期间写手的 worktree 如果变了，本轮审查作废并停下来等人 | Spec AC6、AC13、AC15 |
| FR11 | 上限：门禁尝试次数、审查轮次、无进展分钟数。到了就停 | Spec AC7 |
| FR12 | 写手可以主动求助（说明原因和问题），任务停下来等人回答 | — |
| FR13 | 停下来时，界面给出原因和可选处置，人点一次即可继续或放弃 | Spec AC10 |
| FR14 | 任务面板：状态、门禁历史与日志、审查历史与报告 | — |
| FR15 | 任务列表：所有任务按状态分组 | — |
| FR16 | 人标记"已合并"或"放弃"后，归档 agent 和工作区，保存任务记录 | 记录在 worktree 删除后仍可查看 |
| FR17 | 同时活跃的任务数有上限，默认 3 | 超限时不能启动新任务 |
| FR18 | daemon 重启后，打开界面即可继续，不需要人工修复状态 | Spec AC8 |

### 5.2 P1（有证据再做）

| 编号 | 需求 | 进入条件 |
| --- | --- | --- |
| FR19 | 侦察兵：一次性 worktree 里限时试做，只留报告 | 至少两次因为任务说明写得不对而返工 |
| FR20 | 开工前并行调研，最多 3 个问题 | 用户实际用宿主技能做过三次以上并觉得需要固化 |
| FR21 | 合并一个任务后，其他待合并任务显示"基线已变"，一键要求 rebase 并重新验证 | 出现过一次合并后才发现的冲突或失败 |
| FR22 | 启动时的文件重叠警告 | 同上 |
| FR23 | 每个任务独立的环境变量模板（如 `DATABASE_URL`） | 第一个需要数据库的项目 |
| FR24 | 把"同模型新会话 + 跨家族强模型"做成一键的双审查预设。调研里这个组合抓到的问题明显多于两个同模型审查者。手动添加审查者已在 P0（FR7） | 真实使用中出现过单审查者漏掉阻断问题 |
| FR26 | 门禁标记"新增了跳过测试的标记"和"测试文件净减少"的改动 | 出现过一次靠削弱测试通过门禁 |
| FR25 | 任务级的耗时和 token 统计 | 用户想比较成本时 |

### 5.3 P2（暂不承诺）

一键开 PR 并填入说明（改了什么、为什么、动了哪些文件、风险、门禁输出）；`blocked` 时推送到手机；多假设排查的固化流程。

## 6 怎么判断做成了

不做前置的对照实验（用户决定，2026-11-12）。方案的依据是[调研记录](research.md)，不是一次小样本测试：对照的结论随任务类型、所选模型和 agent harness 变化，每臂三个任务说明不了什么。直接开发，做成与否按下表在真实使用中判断。

### 6.1 成功指标（M2 结束时）


| 指标 | 目标 |
| --- | --- |
| 进入"待合并"的任务里，验收命令实际通过且最终提交经过审查的比例 | 100%（由程序保证） |
| 任务卡在没有提示、没有出路的状态 | 0 次 |
| 用户亲自启动的真实任务 | 至少 10 个走到合并或放弃 |
| 其中不需要人中途介入的比例 | 记录，不设目标 |
| 源码行数 | 不超过 3500 |

## 9 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 没有前置数据证明流程比单 agent 好 | 做完才发现不常用 | 已接受。体量小（3500 行以内），M2 用真实任务观察，不好用就停 |
| 0.15.4 上插件工具的行为与文档不一致 | P0 的核心机制要改 | M1a 先做探针；退路是在 `agent.turn.after` 里读最后一条回复找固定标记 |
| 审查者越出自己的 worktree（共享 `.git`，shell 可以写到别处） | 写手的分支或工作区被改 | 结论提交时检查写手 worktree 的提交和状态，不符即作废并停下 |
| 每个审查者每轮都要准备一个 worktree | 审查变慢，多审查者时更明显 | 探针阶段实测准备耗时；审查 worktree 用完即删，不累积 |
| 验收命令本身不够硬 | 通过门禁但质量差 | 产品不解决这个问题。任务说明模板和文档里强调；受保护路径防止测试被删改 |
| 再次范围膨胀 | 重蹈 v1 | 3500 行硬预算（已放宽过一次，不再放宽）；P1 每项都有进入条件；非目标清单 |
| 宿主后续版本自带了同样的功能 | 插件多余 | 可接受。插件足够小，丢掉成本低 |
| 同家族审查的盲区 | 漏检 | 默认要求不同家族；P1 可加第二审查者 |

## 10 用户决定（2026-11-12）

| 问题 | 决定 |
| --- | --- |
| 是否先做 M0 零代码对照 | **不做，直接开发。** 先前的"同意"已撤回：变量太多（场景、模型、harness），一次小样本测试证明不了什么 |
| Crew Tree 面板 | 不带入 v2，用 Paseo 自带的 Subagents 轨道 |
| 审查者数量 | 默认 1 个，必须可以添加 |
| 审查者的工作目录 | 每个审查者一个独立 worktree，不与写手共用 |
| 审查者的权限模式 | Profile 必须是允许写文件的模式，否则阻止启动；插件不自动放行文件写入 |
| 行数预算 | 总上限 3500 行：服务端按 M1b 现状冻结在 2550 行，界面 900 行。只放宽这一次 |
| M1b 剩余冒烟 | 先用 Claude `auto` 模式的审查者走到 `ready`。Claude 这一段已走通。Codex `full-access` 审查者的冒烟：**用户已批准（2026-11-12）并已走通（N=1）**，仅限 DEV，结果见 M1b 结果第 8 节 |
| v1 的 Role、Team 数据 | 不迁移 |
| 插件 id | 沿用 `paseo-agent-team`，版本从 1.0.0 起 |

下一步是 M1a（探针插件），然后 M1b、M1c。开发不以任何对照实验为前提，不需要 K1–K3 材料、盲审者或对照预算。开发中真正需要用户提供的只有：DEV 实例上的 Agent Profile，以及 Spec 第 18 节的待决问题。
